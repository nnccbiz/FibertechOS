# חקירת חילוץ תמחור ע"י רקסי (Roxy) — מסמך טכני

> נכתב: 15.6.2026 · ענף `claude/fervent-mayer-dn0diw`
> נושא: למה רקסי "ממציאה" פריטים כשמעלים קובץ אקסל לתמחור, מה המערכת אמורה לעשות, ומה תוקן.

---

## 1. תקציר מנהלים

כשמעלים קובץ אקסל של תמחור לכרטיס "תמחור" של פרויקט, **לפעמים מתקבלים 3 פריטים שאין להם שום קשר לקובץ** (למשל: צינור GRP DN800 SN5000 PN10, מחבר אקרובט, ברך 90 מעלות — כולם במספרים עגולים).

**שורש הבעיה:** הפריטים האלה הם **דוגמאות מתוך ההוראות (prompt) של מנוע ה-AI (Gemini)**. הם מופיעים *רק* כש-Gemini מקבל קובץ בלי נתונים קריאים — ואז במקום לקרוא נתונים אמיתיים, הוא משכפל את הדוגמאות שכתובות בהוראות שלו. כלומר: **הקובץ הגיע ל-Gemini במקום להיקרא מקומית, ו-Gemini לא הצליח לקרוא אותו.**

זה לא אמור לקרות: קבצי אקסל אמורים להיקרא **מקומית** (בלי Gemini בכלל) ע"י פרסר ייעודי שכתוב במערכת. הפרסר הזה היה שבור עבור המבנה של תבנית התמחור העברית — וזה תוקן בסשן הזה.

## 2. איך המערכת בנויה — הזרימה המלאה

```
משתמש גורר קובץ אקסל לכרטיס תמחור
        │
        ▼
parseCostFile()  (hooks/usePricing.ts:546)
   1. מנסה לשמור את הקובץ כצרופה (uploadCostInputAttachment)
   2. קורא את הקובץ ל-base64
   3. שולח POST ל-/api/ai עם { message, files: [{base64, mimeType, name}] }
        │
        ▼
/api/ai  (app/api/ai/route.ts)
   ┌─────────────────────────────────────────────┐
   │ לכל קובץ:                                     │
   │   isExcel = שם נגמר ב-.xlsx/.xls  או          │
   │            mime מכיל spreadsheetml/ms-excel   │
   │                                               │
   │   אם isExcel → parseExcelBOQ() — קריאה מקומית │
   │      • מזהה שורות כותרת                        │
   │      • ממפה עמודות (BOQ_COL_MAP / detectCol)  │
   │      • מחזיר פריטים — בלי Gemini בכלל!         │
   │                                               │
   │   אחרת (PDF/תמונה) → נשלח ל-Gemini             │
   └─────────────────────────────────────────────┘
        │
        ▼
חזרה ל-parseCostFile: ממפה את הפריטים ל-cost_input_items
ומציג אותם במצב עריכה (editingCostItems) → המשתמש בודק ושומר
```

**עקרון מנחה (חשוב):** אקסל נקרא **מקומית בלבד**. הסיבה: Gemini נוטה ל"הזות" כשהוא רואה dump לא-מובנה של אקסל, ולכן הוחלט במכוון שאקסל לא ייפול חזרה ל-Gemini — עדיף שגיאה ברורה מאשר נתונים מזויפים.

## 3. מה אמור לקרות (התנהגות תקינה)

עבור קובץ התמחור שנבדק (תבנית עברית, גיליון `תבנית_תמחור`, 37 שורות, שני מקטעים):

| מקטע | תוכן | תוצאה תקינה |
|---|---|---|
| שורות 4–19 | צינורות GRP (8 ארוכים 5.7מ' + 8 קצרים 1מ') | 16 פריטים |
| שורות 27–31 | מחברי שוחה | 5 פריטים |
| **סה"כ** | | **21 פריטים** |

כל פריט עם: DN (300–700), קשיחות SN (10000/15000), לחץ PN (4), אורך, כמות, מחיר למטר — **במטבע ש"ח (ILS)**.

לאחר התיקונים בסשן זה, הפרסר המקומי אכן מחזיר בדיוק את 21 הפריטים האלה (נבדק על הקובץ האמיתי).

## 4. למה זה נכשל — שלוש שכבות

### 4.1 באג ראשי: הפרסר לא זיהה את הכותרות העבריות *(תוקן)*

מילון זיהוי העמודות (`BOQ_COL_MAP`) הכיר רק כותרות כמו `תיאור`, `כמות`, `מחיר יחידה`. הוא **לא הכיר** את הכותרות של תבנית התמחור של פיברטק:

| כותרת בקובץ | היה ממופה ל | בעיה |
|---|---|---|
| `קוטר נומינאלי` | — (לא זוהה) | אין DN |
| `קשיחות (פסקל)` | — (לא זוהה) | אין SN |
| `לחץ בדיקה (PN)` | — (לא זוהה) | אין PN |
| `מחיר מטר ללקוח` | — (לא זוהה) | **אין מחיר!** |
| `מספר פריטים בפועל` | description (בגלל "פריט") | דורס את התיאור |
| `אורך יחידה (מטר)` | unit (בגלל "מטר") | אורך נכנס כיחידה |

בלי עמודת מחיר, הפרסר מחזיר פריטים עם מחיר 0 — או נכשל לגמרי. כשהוא נכשל וזה הקובץ היחיד, המערכת מחזירה שגיאה. **אבל** אם הקובץ איכשהו מגיע ל-Gemini (ראו 4.3) — מתקבלות ההזיות.

**תוקן:** מילון הזיהוי נכתב מחדש להכיר DN/SN/PN/אורך + מחיר עברי (`מחיר מטר`, `מחיר ללקוח`), עם סדר עדיפויות שמונע over-match (`מספר פריטים`→כמות, `אורך יחידה`→אורך).

### 4.2 באג משני: שורות זבל + מטבע שגוי *(תוקן)*

- **שורות זבל:** "אחוז הנחה", כותרת המקטע "מחברי שוחה", ושורת אחוז — עברו כפריטים. **תוקן:** דילוג על שורות בלי כמות ובלי מחיר.
- **מטבע שגוי:** בראש הקובץ יש תא "אירו - דולר | דולר - ש״ח" (טבלת שערי חליפין). הקוד זיהה "דולר" וקבע שכל המחירים בדולר — בעוד שהם בש"ח. **תוקן:** כשמופיעים גם אירו וגם דולר באותה שורה (סימן לטבלת שערים), לא מסיקים מטבע — נשארים בברירת המחדל ש"ח.

### 4.3 הבאג שגורם ל-3 ההזיות: קובץ אקסל שמגיע ל-Gemini ריק

הפריטים שראית — **DN800, מחבר אקרובט, ברך 90** — מופיעים מילה-במילה בתוך ההוראות של Gemini בקובץ `app/api/ai/route.ts`:

- שורה 56: `"...DN2000 ל-DN800..."` (דוגמה לאיסור החלפת קוטר)
- שורה 98: `"Elbow / ברך → elbow"` (מיפוי סוג)
- שורה 96/173: `"מחבר / אקרובט → coupling"`
- SN5000 / PN10 — ערכים גנריים נפוצים של צנרת GRP שהמודל מכיר מאימון

כש-Gemini מקבל **קובץ בלי נתונים קריאים**, הוא לא מחזיר שגיאה — הוא ממלא JSON "סביר" מתוך הדוגמאות שבהוראות שלו + ידע כללי. התוצאה: צינור DN800 + מחבר + ברך, במספרים עגולים. **זו חתימה ודאית של "Gemini ללא נתונים".**

השאלה הנובעת: *למה קובץ אקסל הגיע בכלל ל-Gemini, ולמה ריק?* שתי אפשרויות:

1. **base64 ריק** — בדיקת המסלול היא `if (isExcel && file.base64)`. אם ה-base64 ריק, הקובץ "נופל" ל-Gemini. ב-`processFiles` קובץ עם base64 ריק הופך לטקסט "base64 ריק" → Gemini מקבל אפס נתונים → הזיה. *(נסגר בסשן זה — ראו §6.)*
2. **הקובץ כבד מאוד** — הקובץ שנבדק הוא **749KB** (לא ~15KB כמצופה ל-37 שורות), כי מוטמעות בו **שתי תמונות EMF + קישורים חיצוניים + נוסחאות**. ה-base64 שלו ~1MB. גוף בקשה כבד יכול להישבר/להיחתך בדרך לשרת ולהשאיר `files` פגום.

> **הערה:** עבור הקובץ הספציפי הזה, אחרי התיקונים, הרצה מקומית של הפרסר מחזירה 21 פריטים תקינים. כלומר הקוד הנוכחי *אמור* לקרוא אותו מקומית. אם בפרודקשן הוא עדיין מגיע ל-Gemini — הסיבה היא או base64 ריק/חתוך (גודל), או שנבדק לפני שהפריסה הסתיימה, או שמצב העריכה הציג פריטים ישנים מניסיון קודם.

### 4.4 בעיה נלווית: הצרופה לא נשמרה

בבדיקה מול בסיס הנתונים: לתמחור "Amiblu טורקיה" **אין צרופה ואין קובץ ב-Storage**. כלומר `uploadCostInputAttachment` נכשל (כנראה הגבלת גודל/הרשאת RLS על ה-bucket עבור קובץ 749KB). זה לא מפיל את החילוץ עצמו (הקוד ממשיך), אבל **הקובץ המקורי אובד** — בעיה בפני עצמה ששווה לטפל בה בנפרד.

## 6. מה עוד צריך לקרות (המלצות)

1. **לסגור את חור ה-base64-הריק:** לשנות את התנאי כך שקובץ שזוהה כאקסל **לעולם** לא ייפול ל-Gemini — גם אם ה-base64 ריק. במקרה כזה להחזיר שגיאה ברורה ("הקובץ לא נקרא, נסה שוב"), לא הזיה.
2. **שקיפות מקור החילוץ:** להוסיף לתשובה סימון `extracted_by: 'local_excel' | 'gemini'` ולהציג למשתמש ("חולץ מקומית מאקסל" מול "חולץ ע"י Gemini"). כך נדע מיד באיזה מסלול הלך כל קובץ.
3. **קובץ כבד:** לטפל בקבצים >1MB — או לדחוס לפני שליחה, או לשלוח רק את תוכן הגיליון (טקסט) במקום ה-base64 המלא, או להעלות ל-Storage ולשלוח URL.
4. **כישלון שמירת צרופה:** להבליט למשתמש שהקובץ המקורי לא נשמר (היום זה רק `console.error`).
5. **לנטרל את הדוגמאות הקונקרטיות ב-prompt:** להחליף "DN800"/"ברך"/"אקרובט" בדוגמאות מופשטות (DN&lt;X&gt;), כדי שגם אם Gemini יוזה — הוא לא יוכל לשכפל מספרים שנראים אמיתיים.
